微调 GR00T-N1.7 策略 ── RoboCasa OpenCabinet 开柜子任务

2026-05-29 · Linus 模式 · robocasa-training 仓库 · 配套 training_act.html（ACT baseline）与 act_opencabinet_results.html（ACT 负面结果）

TL;DR：在本机 4090 微调 GR00T-N1.7-3B 攻 RoboCasa OpenCabinet。不是 8bit、不是 LoRA——是 bf16 选择性全参微调：冻结 Cosmos VLM backbone（视觉 + 语言），只训 DiT action head + projector（~560 M 可训练）。4090 24G 靠 adafactor + 梯度检查点 压显存（实测 22.4 GB / 3.5 s/step）。边训边 eval 用 watchdog 单 GPU 串行：训一段 → 杀进程腾显存 → 起 eval server 跑 N 轮 → 杀掉 → resume。配方 1:1 移植自姊妹项目 LeIsaac 的 N1.7 PickOrange recipe，换数据/embodiment 即可。
Finetune GR00T-N1.7-3B on a single 4090 for OpenCabinet. NOT 8bit, NOT LoRA — bf16 selective full-finetune: freeze the Cosmos VLM backbone, train only the DiT action head + projector (~560M trainable). 24G fits via adafactor + gradient checkpointing (measured 22.4 GB / 3.5 s/step). Train-while-eval is a single-GPU serial watchdog. Recipe ported verbatim from the sibling LeIsaac N1.7 PickOrange pipeline.

1. 先回答："是 8bit 全参微调吗？" (What kind of finetune?)

查了姊妹项目 LeIsaac/scripts/finetune/gr00t/ 的 N1.7 配方（launch_finetune_ckpt_n17.py + train_n17.sh），结论直接：

方式用没用说明
选择性全参微调 (bf16) ✅ 这就是答案 冻结 Cosmos 视觉 encoder + LLM backbone（tune_visual=False、tune_llm=False、tune_top_llm_layers=0），全精度训 DiT action head + projector + 线性头，~560 M 可训练（占 3B 的 ~19%）
8bit 量化优化器 (paged_adamw_8bit) ❌ 试过，放弃 4090 N1.6 阶段试过用 bitsandbytes 8bit optimizer 省显存，bnb 0.49.2 在 step 501 resume 时崩。改用 adafactor（无 8bit 依赖、内存占用相当）
LoRA / QLoRA ❌ 没用 GR00T 官方配方就是冻 backbone + 全参训 action head，action head 本身不大（DiT），没必要再 LoRA。LoRA 是给"想训 LLM backbone 又没显存"的场景，这里 LLM 直接冻死
权重 8bit/4bit 加载 (load_in_8bit) ❌ 没用 load_bf16=False + 全 bf16 计算。3B 模型 bf16 权重 ~6 GB，4090 装得下，不需要量化加载
一句话：冻 VLM、全参训 action head、bf16、adafactor + 梯度检查点压显存。8bit 只在"优化器状态"这一层试过且被 adafactor 取代，权重和计算全程 bf16。Freeze the VLM, full-finetune the action head in bf16, squeeze VRAM with adafactor + gradient checkpointing. 8bit was only ever tried at the optimizer-state layer and got replaced by adafactor.

1.1 显存怎么压进 4090 24G 的

手段作用代价
adafactor 优化器不存 Adam 的一阶/二阶动量矩阵，优化器状态从 O(2·params) 降到 ~O(0)收敛略慢于 AdamW，单任务可接受
梯度检查点 use_reentrant=False前向不缓存全部激活，反向时重算 → 激活显存约减半吞吐 ~−30%（这就是 3.5 s/step 的主因）
冻结 VLM backbone2.4 B 参数不需要梯度/优化器状态无（这本就是配方设计）
global_batch=8 / grad_accum=4每步真实 micro-batch=2，激活峰值压到最低需 4 步累积才更新一次
expandable_segments:TrueCUDA 分配器减碎片，避免 OOM 抖动无
本机 4090 实测（来自 LeIsaac N1.7 同配方）：显存峰值 ~22.4 / 24.5 GiB，~3.5 s/step（grad-ckpt 开 + adafactor + micro-batch 2 + torch.compile action_head）。PickOrange 在 ~6000 step 收敛到 14/15 SOTA。Measured on this 4090 via the same N1.7 recipe: ~22.4 GiB peak, ~3.5 s/step, PickOrange converged at ~6000 steps.

2. 为什么训 GR00T-N1.7（而不是 ACT / N1.5）

本仓已经证明：ACT-80M 从头训在 OpenCabinet 上 closed-loop SR 全程 0%（human / mimicgen / temporal-ensembling / pretrain-finetune 四杠杆全试尽，见 ACT 负面结果文档）。对照组 GR00T-N1.5（大规模预训练 VLA）同 eval 管线 70%。差距是模型容量 + 预训练规模。N1.7 是这条正确路线的升级。

策略规模 / backboneOpenCabinet SR本仓定位
ACT (from scratch)80 M / ResNet180%（已验证）负面 baseline，证明小模型从头训不行
GR00T-N1.5（官方 ckpt 直评）2 B / Eagle VLM70%（已验证）当前最强对照（multitask ckpt-120000）
GR00T-N1.7-3B（本文档微调）3 B / Cosmos-Reason2-2B目标 ≥ 70%本仓主攻：单任务专精微调能否超过 N1.5 多任务
假设：N1.5 的 70% 是 18-atomic 多任务 ckpt 的泛化值。在 OpenCabinet 单任务 500 demo 上专精微调 N1.7（更新的 Cosmos backbone + relative action + action_horizon=40），有理由期望 ≥ 70%。这是值得验证的真问题。N1.5's 70% is a multitask generalist. Single-task finetuning N1.7 on 500 OpenCabinet demos should plausibly match or beat it — that's the hypothesis worth testing.

关键适配点：action_horizon。N1.7 的 Gr00tN1d7Config 默认 action_horizon=40，数据侧 action delta_indices 必须对齐 range(40)（data loader 用 horizon = max(delta)−min(delta)+1 推）。panda_omron 内置配置的 action_indices 可能是 16（N1.5 时代），微调 N1.7 前需把它改成 40——这正是 LeIsaac leisaac_config_n17.py 相对 N1.6 唯一的核心改动（range(16)→range(40)）。N1.7 hard-defaults action_horizon=40; the data-side delta_indices must match. This is the one change to carry over.

5. 边训边 eval：单 GPU 串行 watchdog (Train-while-eval)

本机只有一张 4090，训练已占满 22.4 GB——不可能训练和 eval 同时跑。LeIsaac 的 watchdog.sh 解法是时间分片串行，符合"长训必须分 slice + watcher"的铁律：

watchdog 的几个硬核设计（都是踩坑换来的）

  • 串行而非并行：eval 前 wait_gpu_free 3000 90 等 CUDA 驱动真正释放（python 退出后显存还会驻留 ~30 s），必要时 nvidia-smi --gpu-reset 兜底。
  • crash 自动续训：4090 上 N1.x 训练会随机 d.is_cuda() INTERNAL ASSERT 崩。watchdog resume 前 mv optimizer.pt → .bak（丢 adafactor 动量，~50 step 恢复），避免 optimizer.pt 撑爆 transient 显存。
  • eval 阈值自适应：早期 ckpt 跑 fast（3 轮），后期跑 full（6 轮），省早期无意义的 eval 时间。
  • 跳过已评：CSV 第一列记 step，已评的 ckpt 不重复跑。
  • save_steps 强制对齐：HF Trainer resume 时会用 trainer_state.json 里的 save_steps 覆盖 CLI，watchdog 每次 resume 前 patch 一遍。

The parent's N1.5 fork — needed for the working 70% eval — stays untouched.
两棵树各司其职（与 isaaclab 自身做法一致）：mujoco-experience/dependencies/Isaac-GR00T（N1.5 fork）跑 N1.5/N1.7 eval 的 RoboCasa panda_omron 管线；robocasa-training/dependencies/Isaac-GR00T（N1.7 上游）跑 N1.7 训练。N1.7 上游原生支持 RoboCasa 需要的 ActionFormat.XYZ_ROT6D，所以训练侧不需要 fork 任何 RoboCasa 代码，只需注册一个 modality config（见步骤 2）。N1.7 upstream natively supports XYZ_ROT6D, so no RoboCasa fork code needs porting — just register a modality config.

10. 三问自检 (Linus Three Questions)

  • 真问题还是假想？ ✅ 真：ACT 0% 已证明小模型不行，N1.5 70% 已证明 VLA 路线对。N1.7 单任务微调能否超过 N1.5 多任务，是有商业/技术价值的真问题。
  • 有更简单方案吗？ ⚠️ 直接评 N1.5 ckpt 更简单（已 70%），但那是泛化值不是上限。微调是为了拿单任务上限，配方已被 LeIsaac 跑通，移植成本低。
  • 会破坏什么吗？ ❌ 不会：评估端 100% 复用 N1.5 的 ZMQ server/client；训练全在 robocasa-training 仓内新增脚本；唯一外部依赖是换一个带 gr00t_n1d7 的 Isaac-GR00T（不动现有 N1.5 评估环境）。
结论：✅ 值得。配方现成（LeIsaac N1.7），数据现成（OpenCabinet 500 demo 已转 LeRobot），base 现成（本地缓存），eval 管线现成（N1.5 同协议）。唯一新工作是移植 4 个脚本 + 换 Isaac-GR00T 版本。Worth it. Recipe, data, base model, and eval pipeline all already exist — the only new work is porting 4 scripts and swapping the Isaac-GR00T version.
